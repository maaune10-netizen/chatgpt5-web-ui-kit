# Can `deepseek-v4.1-flash` write OpenUI Lang?

**Answer: yes — 26–27 of 27 prompts parse clean, in 6–7 seconds each.** But only
with thinking on. With `thinking: {type:'disabled'}` it drops to 19/27.

Everything below is measured, not estimated. Raw responses for every run are in
the `run-*.json` files next to this report.

```bash
node tools/openui-eval.mjs --effort auto --fix-rules   # the winning config
node tools/openui-eval.mjs --analyze specs/openui-eval/run-*.json
```

## Method

- The system prompt is `openuiLibrary.prompt()` — 28,774 characters (~7,194
  tokens) generated by the installed package, sent unmodified.
- 27 prompts: 24 that ask for an interface, 3 that do not (a sum, a haiku, an
  identity question).
- Every response is judged by `createParser(openuiLibrary.toJSONSchema(), 'Stack')`.
  A run counts as clean only when `root !== null`, `!incomplete`, and there are no
  errors, unresolved references, or orphans.
- Same endpoint, model, temperature (1) and `top_p` (1) the app uses.

## Results

| run | effort | +rules | clean | avg latency | thinking tokens |
|---|---|---|---|---|---|
| 1 | auto | no | **26/27** | 6.2s | 23,386 |
| 2 | off | no | **19/27** | 2.9s | 0 |
| 3 | off | yes | **22/27** | 3.4s | 0 |
| 4 | auto | yes | **27/27** | 6.5s | 22,006 |
| 5 | auto | yes | **26/27** | 7.3s | 29,670 |
| 6 | auto | yes + `inlineMode` | **24/27 render a block, 2/27 correctly prose-only, 1/27 broken** | 6.6s | 26,136 |

Two things fall out of this:

**Thinking is what makes it work.** `off` is 2× faster and 25–30% broken. The
model spends 22k–30k reasoning tokens to get the argument order right; that is
not waste, it is the mechanism.

**The prompt rules help, but only where thinking is off.** 19 → 22. With thinking
on they remove the single largest error class but the score was already 26/27.

## The failure was almost one component

Without the rules, `off` produced 18 errors across 8 responses — **16 of them on
`Card`**:

```
type-mismatch/Card: field "/variant" expects one of ["card","sunk","clear"] but got "column"
type-mismatch/Card: field "/direction" expects one of ["row","column"] but got "m"
```

The model writes `Card([...], "column", "m")`, reaching for `Stack`'s signature.
And OpenUI's own generated prompt invites this — it describes `Card` as
*"Accepts all Stack flex params (default: direction \"column\")"*, while `Card`'s
second positional argument is `variant`. The other trap is `Text`, whose first
argument is an optional `variant`, so `Text("Sell well", ...)` puts the value
where the variant goes.

Two `additionalRules` lines fix both:

```
`Card` and `Stack` do NOT have the same signature. Stack(children, direction?, gap?, ...)
but Card(children, variant?, direction?, gap?, ...). To lay a Card's children out in a row
write Card([...], null, "row", "m") — pass null for variant.

`Text` and `BoldText` take variant FIRST: Text(variant?, value, subtext?, ...).
Write Text("text", "Sell well") or Text("number", "1,284"). The value is never the first argument.
```

With those, the remaining failures change character — they are no longer argument
order but structural: one unresolved reference, one invented `@function`, three
orphaned statements, and one incomplete program. Different problem, much smaller.

## Every answer becomes an interface — unless you turn on `inlineMode`

By default all three non-UI prompts came back as OpenUI Lang:

- `What is 2 + 2?` → a `Card` with `TextContent("4", "large-heavy")` and an explanation line.
- `Write a haiku about rain.` → three `TextContent` lines, a `Separator`, and a `5 · 7 · 5` note.
- `Who are you?` → a `CardHeader`, an intro, and a `ListBlock` of capabilities.

This is the prompt working as designed — *"Your ENTIRE response must be valid
openui-lang code"* — and it is a product decision, not a bug. A chat app that
renders every reply as a component tree is a different product from ChatGPT.

**OpenUI has the escape hatch built in: `inlineMode`.** It teaches the model to
answer in prose and put the interface in a fenced block. Measured on the same 27
prompts, `auto` + rules + `inlineMode`:

| | count |
|---|---|
| responses with a fenced UI block | 24/27 |
| average prose before the block | 223 chars |
| fenced block parses clean | 23/24 |
| answered in prose only — and was right to | 2/27 (`What is 2 + 2?` → `2 + 2 = 4.`; `Who are you?` → an explanation) |
| genuinely broken | 1/27 (`excess-args`: 7 positional arguments to `Stack`, which takes 6) |

So **26 of 27 did the right thing**, and the model chose the right shape on its
own — no router, no toggle. That is the Artifacts pattern: prose stays in the
thread, the fenced block becomes a rendered panel beside it. The thread keeps its
Markdown and its design; the interface gets its own surface.

Re-scored from the stored responses with a corrected fence pattern — the first
extractor used `[a-zA-Z]*` for the language tag and missed `openui-lang`, so it
reported 0 readable fences on 24 responses that all had one. Same data, fixed
extractor, not a fresh run.

## And the loop: not reproduced

The reported loop — *"Let me do it. Let me write. Let me call."* — did not appear
once in 45 two-turn conversations built to provoke it (`tools/loop-probe.mjs`),
across three variants (replaying `reasoning_content` in history, stripping it,
and thinking off) and two effort levels.

Both hypotheses I had are unsupported:

- **Reasoning replay causes it** — no. Replaying `reasoning_content` actually
  produced *shorter* replies (503 vs 799 chars) and was faster (2.3s vs 4.0s).
- **Our "you have no tools" system prompt provokes it** — no. Five prompts
  designed to invite tool calls ("search the web", "read /etc/hosts", "call the
  weather API") never looped.

What is left: it is rare (a tail event 45 samples cannot rule out), it needed a
longer conversation than two turns, or it was a transient on the provider side.
**Without the original conversation I am guessing, and I would rather say so.**
The messages were gone from the database by the time I looked.

### One thing the loop hunt did produce

The first loop detector was wrong. It counted how often any 5-word sequence
repeated anywhere in a response, which flagged **4 of 27 perfectly good replies** —
all of them tables and card blocks, where rows repeat by nature
(`{left: "Opened", right: ...}` × 10). *Resemblance is not a loop.*

The corrected metric (`tools/loopiness.mjs`) measures **consecutive** repetition:
a run of identical lines, or a repeat at a period of 1–5 sentences — which is the
shape of the reported loop. On the same 27 stored responses it reports 0/27.

That metric is now validated in both directions: it fires on nothing legitimate,
and it is the one to build a guard on.

## Recommendation

**Worth building, as a panel beside the reply, with `inlineMode` on.**

- `inlineMode` + the two rules is the configuration: 24/27 render a UI block,
  2/27 correctly answer in prose, 1/27 breaks. The model picks the shape itself.
- Keep thinking on for this feature. It is the difference between 96% and 70%,
  and it is what pays for the argument order.
- Do not replace the thread's Markdown with a component tree. Prose stays prose;
  the fenced block gets a panel — which is also what ChatGPT does with Artifacts,
  so the design parity this project is built on survives.
- Do build the loop guard, on the consecutive metric. The failure is cheap to
  detect and expensive to show.
