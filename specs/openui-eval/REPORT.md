# Can `deepseek-v4.1-flash` write OpenUI Lang?

**Answer: yes — 26–27 of 27 prompts parse clean, in 6–7 seconds each.** But only
with thinking on. With `thinking: {type:'disabled'}` it drops to 19/27.

Everything below is measured, not estimated. Raw responses for every run are in
the `run-*.json` files next to this report.

```bash
node tools/openui-eval.mjs --effort auto --fix-rules   # the winning config
node tools/openui-eval.mjs --analyze specs/openui-eval/run-*.json
```

## Method

- The system prompt is `openuiLibrary.prompt()` — 28,774 characters (~7,194
  tokens) generated by the installed package, sent unmodified.
- 27 prompts: 24 that ask for an interface, 3 that do not (a sum, a haiku, an
  identity question).
- Every response is judged by `createParser(openuiLibrary.toJSONSchema(), 'Stack')`.
  A run counts as clean only when `root !== null`, `!incomplete`, and there are no
  errors, unresolved references, or orphans.
- Same endpoint, model, temperature (1) and `top_p` (1) the app uses.

## Results

| run | effort | +rules | clean | avg latency | thinking tokens |
|---|---|---|---|---|---|
| 1 | auto | no | **26/27** | 6.2s | 23,386 |
| 2 | off | no | **19/27** | 2.9s | 0 |
| 3 | off | yes | **22/27** | 3.4s | 0 |
| 4 | auto | yes | **27/27** | 6.5s | 22,006 |
| 5 | auto | yes | **26/27** | 7.3s | 29,670 |
| 6 | auto | yes + `inlineMode` | **24/27 render a block, 2/27 correctly prose-only, 1/27 broken** | 6.6s | 26,136 |

Two things fall out of this:

**Thinking is what makes it work.** `off` is 2× faster and 25–30% broken. The
model spends 22k–30k reasoning tokens to get the argument order right; that is
not waste, it is the mechanism.

**The prompt rules help, but only where thinking is off.** 19 → 22. With thinking
on they remove the single largest error class but the score was already 26/27.

## The failure was almost one component

Without the rules, `off` produced 18 errors across 8 responses — **16 of them on
`Card`**:

```
type-mismatch/Card: field "/variant" expects one of ["card","sunk","clear"] but got "column"
type-mismatch/Card: field "/direction" expects one of ["row","column"] but got "m"
```

The model writes `Card([...], "column", "m")`, reaching for `Stack`'s signature.
And OpenUI's own generated prompt invites this — it describes `Card` as
*"Accepts all Stack flex params (default: direction \"column\")"*, while `Card`'s
second positional argument is `variant`. The other trap is `Text`, whose first
argument is an optional `variant`, so `Text("Sell well", ...)` puts the value
where the variant goes.

Two `additionalRules` lines fix both:

```
`Card` and `Stack` do NOT have the same signature. Stack(children, direction?, gap?, ...)
but Card(children, variant?, direction?, gap?, ...). To lay a Card's children out in a row
write Card([...], null, "row", "m") — pass null for variant.

`Text` and `BoldText` take variant FIRST: Text(variant?, value, subtext?, ...).
Write Text("text", "Sell well") or Text("number", "1,284"). The value is never the first argument.
```

With those, the remaining failures change character — they are no longer argument
order but structural: one unresolved reference, one invented `@function`, three
orphaned statements, and one incomplete program. Different problem, much smaller.

## Every answer becomes an interface — unless you turn on `inlineMode`

By default all three non-UI prompts came back as OpenUI Lang:

- `What is 2 + 2?` → a `Card` with `TextContent("4", "large-heavy")` and an explanation line.
- `Write a haiku about rain.` → three `TextContent` lines, a `Separator`, and a `5 · 7 · 5` note.
- `Who are you?` → a `CardHeader`, an intro, and a `ListBlock` of capabilities.

This is the prompt working as designed — *"Your ENTIRE response must be valid
openui-lang code"* — and it is a product decision, not a bug. A chat app that
renders every reply as a component tree is a different product from ChatGPT.

**OpenUI has the escape hatch built in: `inlineMode`.** It teaches the model to
answer in prose and put the interface in a fenced block. Measured on the same 27
prompts, `auto` + rules + `inlineMode`:

| | count |
|---|---|
| responses with a fenced UI block | 24/27 |
| average prose before the block | 223 chars |
| fenced block parses clean | 23/24 |
| answered in prose only — and was right to | 2/27 (`What is 2 + 2?` → `2 + 2 = 4.`; `Who are you?` → an explanation) |
| genuinely broken | 1/27 (`excess-args`: 7 positional arguments to `Stack`, which takes 6) |

So **26 of 27 did the right thing**, and the model chose the right shape on its
own — no router, no toggle. That is the Artifacts pattern: prose stays in the
thread, the fenced block becomes a rendered panel beside it. The thread keeps its
Markdown and its design; the interface gets its own surface.

Re-scored from the stored responses with a corrected fence pattern — the first
extractor used `[a-zA-Z]*` for the language tag and missed `openui-lang`, so it
reported 0 readable fences on 24 responses that all had one. Same data, fixed
extractor, not a fresh run.

## The loop: found, and it was not a loop

**Correction.** The first version of this report said the loop did not reproduce.
Then the conversation turned up in the database — I had looked before it was
there. Here is what it actually is.

### The evidence

The stored assistant message had `content: 0` and `reasoning: 16,804` — sixteen
thousand characters of thinking and **not one character of answer**. The user had
pressed Stop (`stopped: 1`).

The user prompt was 7,611 characters asking for something impossible: *"Produce
the actual video using Hyper Frames and the available video-generation, animation,
editing, and audio capabilities."* Our system prompt says the model has no tools
and no internet. So it could not do it — and instead of saying so, it did all the
work **inside the reasoning channel**: the script, the Arabic captions with
timestamps, and the full HTML and Remotion code.

### Re-run to measure it

Same prompt, same system prompt, no stop:

| | |
|---|---|
| wall clock | **156 seconds** |
| first byte | 1,558 ms |
| reasoning | 46,468 chars · 14,936 reasoning tokens |
| visible answer | 33,786 chars |
| `finish_reason` | `stop` |
| `Let me …` in the reasoning | **36 times** |
| `loopiness` on the reasoning | `periodRun=1`, `lineRun=1` → **not a loop** |

The answer it finally wrote opens with exactly the right thing:

> ## 1. Capability check (honest, read this first)
> | Requested | Status here |
> | Hyper Frames project / renderer | **Not available.** I have no tools, no shell,
> no filesystem, no renderer in this chat…

### So what the user saw

*"Let me do it. Let me write. Let me call."* is not repetition. It is **36
different planning steps** — *let me think about Kimi*, *let me design the HTML*,
*let me write the JS*, *let me write out the full HTML*, *let me produce the final
answer* — streaming past for two and a half minutes while the answer stayed at
zero characters. Stopping it at that point is entirely reasonable, and it is why
`content` was empty.

Three things follow, and none of them is a loop guard:

1. **The metric was right.** `loopiness` reports `periodRun=1` on the real
   incident. Resemblance is not a loop — now validated against a true positive
   case as well as against 27 healthy responses.
2. **The real symptom is time-to-answer, not repetition.** 156 seconds with no
   output is indistinguishable from being stuck, because nothing on screen says
   otherwise. A thinking counter — elapsed time and reasoning tokens — would have
   made it obviously alive.
3. **The trigger is a request that exceeds the model, and the fix is in the
   system prompt.** It already says "you have no tools". It does not say *"if a
   request needs something you do not have, say so on the first line and offer
   what you can do — do not plan a way around it."* That one sentence turns a
   156-second silence into a two-second answer, and the model already writes that
   capability check unprompted when it finally gets there.

My 45-conversation probe missed it because every prompt in it was answerable. The
trigger is not conversation length or reasoning replay — it is **a task the model
cannot do**. That is a much narrower and more useful finding than "it sometimes
loops".

The earlier hypotheses stay dead: `reasoning_content` replay made replies shorter
and faster, and our "no tools" line is not the cause by itself — the missing half
is that it never says what to do instead.

## Recommendation

**Worth building — and it is now built, as a card in the thread with a Canvas.**

`inlineMode` + the two rules is the configuration: 24/27 render a UI block, 2/27
correctly answer in prose, 1/27 breaks. The model picks the shape itself.

What shipped:

- `src/generated/openui-prompt.txt` — the OpenUI prompt with the rules, generated
  at build time by `tools/openui-prompt.mjs`, so the 2 MB library is not needed to
  *send* a system prompt.
- `src/app/GenUI.tsx` — the renderer, lazy-loaded. `src/app/genui-shared.tsx` —
  the context and `isGenUILang`, tiny, so `Markdown.tsx` does not pull the weight.
- A ```openui-lang fence renders as a card with **Code** and **Canvas**.
- `@ToAssistant` sends a message, `@OpenUrl` opens the tab.
- Settings → **Generative UI**. It replaces the system prompt rather than adding
  to it, because two competing instructions fight.

Measured on the built app: the library is not requested until a UI block actually
arrives (0 requests on load, 3 after), 13/13 assertions, 0 page errors, and a
clicked button starts a real turn.

Keep thinking on for this feature. It is the difference between 96% and 70%, and
it is what pays for the argument order.

## Speed: where the time actually goes

The first version felt slow. Measured, the wait was in two places and only one
of them was the model.

**The model, 3–6s, and it does not move.** `reasoning_effort: low` was no faster
than `auto` (6.5s vs 6.5s) even though it produced 15,212 reasoning tokens
against 22,006 — the wall clock is dominated by the program it writes, not by the
thinking. `off` is genuinely 2× faster (2.9s) and costs 25–30% of responses
(19/27 without the rules, 22/27 with them, against 26–27/27 with thinking on).
So this part is a quality/speed trade the user makes, not something to tune away.

**The renderer, which was ~1s of pure dead wait.** `@openuidev/react-ui` is
**12 MB in dev** (2 MB in production) and it was being fetched *after* the answer
arrived, so the card sat on "Loading the UI renderer…" while the user had already
read the prose. The model spends 3–6s thinking; the chunk fits inside that
window with room to spare.

`preloadGenUI()` now fires when the message is sent (and when the toggle is
switched on), so the fetch runs in parallel with generation:

| | before | after |
|---|---|---|
| chunk requested | after the answer | **+1.1s after send** |
| chunk transfer | — | 967 ms (12 MB, dev) |
| UI visible relative to the answer | **~+1,000 ms after** | **162 ms before** |

The last line is the one that matters: the interface now draws while the answer
is still streaming, so there is nothing left to wait for once the prose ends.

### Still open

The thinking counter and the capability-check rule from the section above are not
built yet. They are the two things that would have prevented the incident.
